- [ ] **Move towards a more iOS native feel for our own styled components (motion).** iOS interactives move, morph and animate; ours just appear. Selects, popovers, menus and most other interactive parts show up and vanish instantly and feel clunky. The bottom sheet is the only part with real animation (`ui/sheet/Sheet.tsx`: a fixed duration `withTiming` slide of the panel plus a fading backdrop) and even that feels clunky. Only four files use Reanimated today (`ui/sheet/Sheet.tsx`, `ui/inset-page.tsx`, `screens/period-swipe.ts`, `screens/TimeGrid.tsx`); `react-native-reanimated` 4.5 and `react-native-gesture-handler` are installed. Goal: our custom components behave like iOS system ones, still looking like the desktop app but moving like iOS. **General rule for all mobile motion: copy Apple's iOS animation style.** Custom animations that feel interactive and physical, driven by springs and by the finger rather than by canned timelines. The most important property of great iOS animation is that it is **interruptible and cancellable**: touch a moving sheet, menu or drawer and it stops under the finger at its current position and velocity (nothing jumps or restarts); let go and it **springs** to wherever the gesture points, carrying the release velocity; dragging is always 1 to 1 with the finger with rubber banding at the limits; a tap during an animation reverses it smoothly instead of waiting for it to finish. So: animate with Reanimated springs (`withSpring`, with `velocity` from the gesture) and gesture handler pans, keep animation state in shared values that gestures can take over at any moment, never a fixed duration timeline for anything a user can interrupt, and never block input during an animation. Match iOS spring feel (about 0.3 to 0.5 s response, light overshoot only where iOS overshoots) and put these values in the one shared motion token file. Add this as a rule to the mobile section of `AGENTS.md` and a decision to `DECISIONS.md`, and write tests that interrupt animations (start, interrupt mid way, check it continues from the current value) where the logic is testable. Do it through shared building blocks (one motion token file with the springs, durations and easing, one place per component kind), never per screen tweaks. Concretely:
  - Sheet: spring based (interruptible, velocity carrying) instead of fixed duration timing; drag to dismiss follows the finger and settles with the release velocity; the backdrop fades with the panel's position; detents (medium and large) with rubber banding at the edges; content and keyboard resize smoothly; a small handle; dismissal by swipe down anywhere on the header or non scrolling content.
  - Menus, selects and popovers (see the item above about simple selects): scale and fade in from the trigger's anchor point with a spring, the way iOS context menus and pull down menus do, and morph out of the trigger where it makes sense; rows highlight on press with a soft highlight and tracking finger drag across rows; dismiss with a quick fade.
  - Pressables: a subtle press scale or highlight with a quick spring back on buttons, rows, tabs, chips, and the checkbox (check mark drawn in), toggles and tab changes with animated selection (a sliding indicator, not an instant switch), list changes (add, remove, reorder, expand and collapse of groups, sub-tasks) animated with layout transitions, screen transitions and drawers that follow the finger.
  - **Custom haptics, which Apple itself barely does but the user loves.** Use the Taptic Engine deliberately as part of the design: every meaningful interaction gets a haptic that matches its motion (a soft tick when a select or picker value changes, a crisp click when a toggle or checkbox flips, a rising tap as a task is completed, a thud when a sheet settles on a detent or hits an edge, a light bump as a drag crosses a row or the sidebar opens, a distinct pattern for success, a conflict and an error). `expo-haptics` only gives the presets (impact, selection, notification) and is fine for a first pass, but the real thing is **Core Haptics** (`CHHapticEngine`, transient and continuous events with intensity and sharpness curves, played from the gesture's own progress so the feel tracks the finger). Build a local Expo module for it, next to the existing Swift module `apps/mobile/modules/nookly-keys` (for example `modules/nookly-haptics`), and wrap it in one `haptics` API with named patterns (`tap`, `select`, `toggle`, `success`, `detent`, `edge`, `error`, ...) so screens never touch the engine.
